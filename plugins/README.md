# 工作台模块约定

当前是源码内置插件注册机制，不是第三方插件市场。Alum4K 的业务实现暂时仍保留在原 `src`、`server` 文件中，本次不搬迁媒体库与账号数据，也不声称已经生成可独立安装的插件包。

AlumWindows 清单位于 `plugins/alumwindows/manifest.ts`；前台 `src/WindowsApp.tsx`、后台 `src/WindowsAdmin.tsx`、服务端 `server/windows*.ts`，路由固定为 `/windows` 与 `/windows/admin`。初始公开资源快照随插件源码发布，后续运行数据独立保存在 `data/windows/`。管理员登录沿用统一账号，不注册新默认密码。

## 清单与配置

每个模块在 `plugins/<id>/manifest.ts` 声明 `schemaVersion`、`id`、`version`、名称、说明、分类、前台入口、后台入口、图标和 Logo，并满足 `shared/plugins.ts` 的类型。通过 `shared/workbench.ts` 的 `pluginRegistry` 注册。

路由、版本和 Logo 来自受版本控制的清单。管理员仅能改名称、说明、排序及启用状态，不能让配置文件注入路由或执行代码。新增模块需要明确接入前端懒加载路由、服务端路由、权限检查和 Nginx 规则，并添加测试，而不是只增加一张不能打开的入口卡片。

`data/workbench.json` 独立于影视设置；更新脚本会备份整个 `data`。新内置模块自动取得默认配置，不覆盖已有设置。关闭模块不删除业务数据，仍允许管理员进入模块后台恢复服务。工作台的收藏、最近访问和主题按浏览器本地保存，不作为服务器访问统计。

## 后续可打包边界

- 清单与静态资源：固定模块 ID、版本、相对资源路径及唯一 URL 前缀。
- 前端：独立懒加载入口，不向其他模块注入全局 UI 状态。
- 服务端：显式注册业务路由，继续使用统一账号校验，数据保存在模块自己的目录。
- 升级：声明兼容版本、数据迁移与回滚步骤，安装前检查路由冲突。
- 发布：第三方包安装需要签名/来源验证、资源与权限约束，不能直接解压并执行用户上传代码。

Alum4K 的历史 `/api/...` 暂不重命名，以兼容已有采集器和客户端；后续 API 版本迁移需要单独的兼容周期。

## 个人桌面

`shared/dashboard.ts` 的小组件清单定义待办、项目、便签和日历，数据及布局从 `/api/workbench/me` 读取，依登录账号隔离。小组件不能借用管理员接口读取其他用户的内容。当前渲染与交互集中在 `src/PersonalWorkspace.tsx`，尚未分发为独立安装包；后续拆包应沿用该清单与按账号隔离的存储约定。

保存使用递增版本号。插件不能忽略 409 冲突后强行重试覆盖；应保留草稿，允许用户导出并重新读取。公开首页 SSR 和公开模块清单不包含个人工作空间数据。
